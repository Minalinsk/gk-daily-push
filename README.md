# 每日时政推送

每天凌晨自动跑一次，往企业微信里推**一条**消息：**前一天的热门时政**（给申论攒素材）。
**内容超长会自动拆成多条发**，不会截断丢内容。

跑在 GitHub Actions 上：**零成本、零服务器、零第三方依赖**——只用 Python 标准库，不需要 `pip install`。

- **抓取**：6 个时政源（含《求是》官网，最权威的理论文章）
- **定时**：每天跑**一次** —— cron 北京时间 **02:30** 叫醒工作流，再随机等 0~15 分钟就开抓开推。
  ⚠️ **cron 是"叫醒"的时刻，不是送达时刻**：GitHub 的 schedule 实测会晚 2.4~7.6 小时派活，
  所以实际收到大概率落在北京 **05:20~10:05** 之间，每天不定。这是明确接受的取舍 ——
  要的是"每天稳定跑一次"，而不是"固定在某一分钟收到"。想改成固定时刻见「改推送时间」那一节
- **超长自动分条**：单条消息装不下就拆成多条发（带 `（1/3）` 这样的序号），不截断丢内容
- **推送**：企业微信群机器人，markdown 消息
- **去重**：推过的链接记进 `state/seen.json`，提交回仓库，只推新内容（内容没变就不写盘、不提交）
- **保活**：`keepalive.yml` 每月 1 号看一眼，距上次提交超过 20 天才补一个提交，保证仓库 60 天内一定有过提交
- **容错**：任何环节出错都会推一条失败通知（带错误类型 + 日志尾部），不会静默死掉
- **源健康**：某个源连续 2 天抓不到，会在推送消息末尾挂一行 `⚠️ 抓取异常：… 连续 N 天`（以前只在 Actions 日志里留一行，坏了好几天都没人发现）
- **国内站点适配**：自动识别 GBK/gb18030 编码；政府站点证书链有问题时自动降级重试

想自己搭一套？直接看下面的 [部署（5 分钟）](#部署5-分钟)。

## 它做什么

1. 每天自动跑**一次**：cron 在北京时间 **02:30** 叫醒工作流，再随机等 0~15 分钟开抓（实际送达约 05:20~10:05，见上）
2. 抓 6 个时政源的列表页（**先把整页扫完，再按日期/关键词过滤，最后才按 `max` 截断**）
3. 挑出**前一天**的要闻，每条自动挂一个考点标签
4. 组装消息，超长就拆成多条
5. 把推过的链接提交回仓库，下次只推新的

效果长这样：

```
📰 每日时政 · 09-20

新华网·时政
- 中国空间站“太空厨房”全面升级 航天员20分钟吃上热食
- 多部门将重拳整治生态环境监测机构弄虚作假问题
央视网·要闻
- 生态环境部：重拳整治环境监测造假！
中国新闻网·要闻
- 1至8月中国铁路发送旅客人次创历史同期新高
...

共 22 条 · 07:12 推送
```

## 每日时政怎么挑

- 每条会自动挂一个**考点标签**（`topics.py`），扫一眼就知道值不值得点开：
  `- 【新质生产力】我国成功发射秦岭卫星01、02星等9颗卫星`
  - 13 个考点：新质生产力 / 经济高质量发展 / 乡村振兴 / 生态文明 / 民生保障 /
    就业教育 / 法治建设 / 文化建设 / 党的建设 / 基层治理 / 改革开放 / 国际外交 / 安全应急
  - 关键词匹配，命中最多词的那个胜出；一个都没命中就不挂标签（不显示「综合」这种空标签）
  - 想让标签不出现：`config.TOPIC_TAGS = False`
- 看哪一天由 `NEWS_DAY` 决定（在 workflow 里设）：
  - **定时那次 → 前一天**（昨晚的新闻）
  - 手动触发 → `auto`，按当前时间自动判断（`NEWS_WINDOW_AUTO`，过了中午 12 点算"今天"）
  - 为什么按 cron 定死、而不是按"现在几点"猜：排队晚点可能跨过中午 12 点，
    靠猜会把内容切错（凌晨那次会被切成"今天"，而那天新闻还没几条）
  - 想固定成某一天：把 `NEWS_DAY` 设成 `"today"` / `"yesterday"`（环境变量也行）
- 优先取 URL 日期正好是目标那天的条目；某个源那天没更新时，
  退而取它最新的 `NEWS_FALLBACK_MAX = 3` 条，免得整个源缺席
- 按源轮转着拿（`MAX_PER_SOURCE = 12`，总共 `MAX_TOTAL = 24`），
  消息里按源归拢；推过的链接记进 `state/seen.json`，只推新的。
  这些条目如果一条消息装不下，会自动**拆成多条**发（见「消息太长会怎样」）

### 为什么没有公考公告源

这个仓库以前还有一条「⏰ 考试日程提醒」——抓招考公告正文、抽出报名/考试时间，每天单独推一张时间表。
**2026-10-08 已整体移除**：那 7 个公告源（山西省考 / 华图全国公务员 / 华图全国事业单位 /
中公全国事业单位 / 华图山西公务员 / 粉笔招考公告）只为那条提醒服务、不进时政清单，
每轮还要额外抓 40 篇 100~250KB 的正文，单独占 5~15 分钟。

现在仓库只做时政。想找回公告那条线，见 git 历史里删除前的版本。

关于那几个源当年踩过的坑（留个记录，省得以后重蹈）：

- **公考雷达** —— 挂了**阿里云 WAF**，返回的是混淆过的 JS 挑战页（要浏览器算出 `acw_sc__v2` cookie），纯脚本抓不了，放弃。
- **国家公务员局 / 人社部官网** —— JS 挑战或 403，抓不动；国考消息只能靠媒体和培训机构转载覆盖。
- **粉笔** —— 首页是**服务端渲染**的，能拿到标题和链接；但它的资讯列表页（`/page/exams-information-list`）是**前端渲染**的，HTML 里啥都没有，抓不到。
- **华图 / 中公** —— 能抓，但页面是 **GBK 编码**（`fetcher.py` 已做了自动识别）；另外华图全国页是**按省份分段排版**的，`max` 开小只能吃到最前面几个省。
- **华图 / 中公 / 粉笔的噪音** —— 列表页里混着大量"行测每日一练""上岸血泪教训"这类内容农场文章，当年的处理办法是一组关键词黑名单（`STUDY_NOISE`），已随公告源一起删除。

**⚠️ 官方 RSS 早就停更了。**
人民网 RSS 停在 2025-06，教育频道甚至停在 2016 年；新华网 RSS 也是几年前的内容。所以本项目是**直接解析网页**，不是读 RSS——这样拿到的才是当天新闻。

**✅ 求是网（《求是》官网）—— 能抓，但没有 RSS。**
- `/rss/*.xml` 全部 404，所以直接抓**首页**：文章链接形如 `https://www.qstheory.cn/20260920/<32位hex>/c.html`，一页 37 条左右，能覆盖最近几天的理论文章
- 好处是**不用抓正文就有标题**（标题就在 `<a>` 里），而且 URL 里就带日期（`/20260920/`），"只取目标那天"的过滤直接生效
- ⚠️ 这是政府站，GitHub Actions 的海外机房可能连不上。连不上只记一条日志，不影响其他源——本地跑或放在国内机器上跑最稳

## 注意：GitHub 的机器在国内站点上会被区别对待

这是实跑对比出来的（同一套代码，本地 Windows 和 GitHub Actions 各跑一次）：

| 源 | 本地 | GitHub Actions | 说明 |
|---|---|---|---|
| 求是网 | ✅ | ⚠️ 看情况 | 政府站，海外机房偶尔连不上，连不上只记日志 |
| 新华网 / 人民网 / 央视网 / 中新网 | ✅ | ✅ | 能抓到 |
| 新华网·时政 `/politics/` | ✅ | ✅ | 是**推荐聚合页**，稿子普遍滞后 3~12 天，所以窗口放宽到 7 天 |
| 央视网·要闻 | ✅ | ✅ | 但首页一页只匹配到 3~9 条当天稿（页面本身不是完整列表） |

单源失败不影响其他源，也不会让任务失败。**同一个源连续失败 2 天以上时，会在推送消息末尾挂一行 `⚠️ 抓取异常：… 连续 N 天`** —— 以前只在 Actions 日志里留一行 `抓取失败`，坏了好些天都没人发现（日志是没人天天翻的）。

想更稳（比如补官方一手），在**国内 IP** 上跑一份更省事：一台常开的小机器，配个 cron 就是每天 `python main.py`。在 Actions 里挂代理要额外服务和维护，不划算。

## 部署（5 分钟）

### 1. 建仓库

新建一个仓库，比如 `gk-daily-push`。

**这里建议用公开仓库**：公开仓库的 Actions 完全不计费，私有仓库每月只有 2000 分钟免费额度。
本项目一天只跑一次（随机等 0~15 分钟 + 抓取 2~3 分钟）：
单次约 20 分钟，**一个月约 600 分钟** —— 公开仓库不计费，私有仓库那 2000 分钟额度也够用。
（之前那种"提前几小时把任务拉起来、在任务里等到点"的做法单次要占 300 分钟，
是现在这套的十几倍，也正是私有仓库扛不住的原因。）

### 2. 传文件

**目录结构不能变**：

```
gk-daily-push/
├─ main.py
├─ config.py
├─ fetcher.py
├─ topics.py
├─ push.py
├─ state.py
├─ log_utils.py
├─ .gitignore
└─ .github/
   └─ workflows/
      ├─ daily.yml       ← 必须在 .github/workflows/ 下，放根目录不生效
      └─ keepalive.yml   ← 同上
```

⚠️ 如果仓库首页能直接看到 `daily.yml`，就是传错了位置。

### 3. 配 Secrets

仓库 → **Settings** → **Secrets and variables** → **Actions**

**Secrets**（New repository secret）：

| Name | Value |
|---|---|
| `WEWORK_WEBHOOK` | 企业微信群机器人 Webhook 地址（形如 `https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=xxxxxxxx`，从群机器人设置里复制完整，末尾的 `key=` 不能少） |

**Variables**（可选）：`WEWORK_MSG_TYPE` = `markdown`

> 仓库是**公开**的话，Webhook 必须放在 Secrets（加密）里，别放 Variables——Variables 是明文。

### 4. 启用并测试

仓库 → **Actions** → 左侧 `gk-daily-push` → **Run workflow**，两个勾选项：

| 勾选 | 作用 |
|---|---|
| `test_push` | **只发一条测试消息**（不抓取、不动索引）—— 刚配完 Webhook 时用它验证通道 |
| `dry_run` | 真抓取、真解析，但**不推送**，结果只写进 Actions 日志 —— 用来预览内容（本地更推荐 `simulate.py`，见下面的「本地预览」） |

**首次运行只建索引、不推内容**，你会收到一条「已就绪」的提示——避免第一次被几百条历史链接刷屏。
想测试时就看到完整效果：把 `config.py` 里 `FIRST_RUN_PUSH` 改成 `True`，测完改回来。

## 怎么改

### 加一个源

```python
{
    "name": "显示名",
    "url": "列表页地址",
    "pattern": r"文章链接的正则",
    "max": 8,
},
```

`pattern` 怎么写：打开列表页 → 点开一篇文章 → 看 URL 规律。

例：`https://www.news.cn/politics/20260920/e6f43.../c.html`
→ 正则 `news\.cn/politics/\d{8}/\w+/c\.html`

**一条源还支持这几个可选字段：**

| 字段 | 作用 |
|---|---|
| `title_pattern` | 标题不在 `<a>` 里时，用它从链接后面 500 字里捞标题 |
| `include` | 本源专用白名单，标题不含这些词就不推 |
| `exclude` | 本源专用黑名单 |
| `max` | 本源最多**收下**几条（注意是"收下"的条数，不是"扫过"的条数）。**宁可开大**——真正压量的是 `max_age_days` 和去重索引；开小了，分栏排版的页面只能吃到最前面一两栏。`extract_articles` 现在是「先扫完整个列表页 → 按日期/关键词过滤 → 最后才用 `max` 截断」，所以"页面靠前的旧文把配额占满"这个老毛病没有了 |
| `max_age_days` | 覆盖全局的日期限制（更新慢的源可以放宽到几十天） |

### 源的顺序会影响入选优先级

推送时按源轮转挑选（每个源先各拿 1 条，再各拿第 2 条……），
所以把**最不该漏的源放前面**（现在是求是网排第一）。
源在 `SOURCES` 里的位置同时决定消息里各源分组的先后。

### 换成本省源 / 只看某个省

各省人事考试网一般长这样：`rst.<省>.gov.cn/rsks/`。
想只留某省的内容，给源加一行 `"include": ["山西"]`（标题含「山西」才推）。

### 只推考公相关内容

```python
INCLUDE_KEYWORDS = ["公务员", "招录", "选调", "事业单位", "考试", "公告", "面试"]
```

留空 `[]` 就是不筛。注意这是**全局**规则（会连同所有源一起筛）。只想筛某一个源，用那个源的 `include`。

### 改推送时间

改 `.github/workflows/daily.yml` 的 cron 就行，**写的是 UTC 时间**（北京减 8 小时）：

| 项 | 现在的值 |
|---|---|
| cron | `30 18 * * *` = UTC 18:30 = **北京 02:30** |
| 触发后做什么 | 随机等 0~15 分钟 → 抓取 → 推送 |
| 实际送达 | **不固定**，实测大概率落在北京 **05:20 ~ 10:05** 之间 |
| 看哪一天的要闻 | **前一天**（`NEWS_DAY=yesterday`） |

⚠️ **关键：cron 是"叫醒工作流"的时刻，不是送达时刻。**
本仓库实测过，GitHub 的 `schedule` 是**系统性晚点**，不是差几分钟：

- cron UTC 18:07（北京 02:07）实测晚 **2.8 ~ 5.0 小时**
- cron UTC 06:07（北京 14:07）实测晚 **5.2 ~ 7.6 小时**
- 2026-10-04 ~ 10-08 连续五天用 cron UTC 18:30 实测：晚 **3.1 / 3.3 / 5.7 / 4.2 / 4.7 小时**，
  实际到达落在北京 **05:38 ~ 08:14**

而且每次 run 的 `created_at` 都等于 `run_started_at` —— 说明**晚点全部发生在
GitHub 的 cron 调度层**（它自己拖几小时才创建这个 run），不是 runner 排队不够用。

所以现在这套是**明确取舍**：要的是"每天稳定跑一次、大概清晨到上午到"，
而不是"固定在某一分钟收到"。凌晨 02:30 叫醒，实际 05:20~10:05 之间到，每天不定。

### 消息太长会怎样：自动拆成多条，不丢内容

**不会截断，会拆条发**（`main.build_messages`）：

- 按 `config.MSG_BUDGET`（3400 字节）分页，每页标题带序号：
  `**📰 每日时政 · 10-04（2/3）**`。跨页时会**重新打一次源标题**，所以单看某一条也不会迷路。
- **摘要行**（`共 N 条 · HH:MM 推送`）和**源告警**只挂在最后一条上。
- 只有**真正发出去的页**里的条目才记进索引；没发出去的下次还会推，不会丢。
  某一条发送失败就停在那儿，下次整体重推，不会出现"只发出去半截"的状态。

企业微信 markdown 正文上限是 4096 字节，分页预算 3400 是给它留的余量
（标题/摘要/告警都在这段余量里）。即使极端情况下单页仍然超长，
`push._truncate` 会**按行**兜底截断 —— 不会把 markdown 的 `[标题](链接)` 切成两半。

#### 如果以后想改成"稳定落在某个时刻"

做法是：**把 cron 提前到目标时刻之前**（提前量要大于最大晚点 ~7.6 小时），
然后在 job 里等到目标时刻再动手：

1. **先定窗口 [A, B]**：几点到几点之间必须收到消息。
2. **目标时刻 T 取窗口开头**。GitHub 的晚点只会让消息**更晚**、不会更早，
   所以 T 越晚，能容忍的迟到就越少 —— 把 T 放在窗口前面，等于把窗口剩下的时间当缓冲。
3. **提前量 L 用来吃晚点**，必须大于最大晚点。⚠️ GitHub 单个 job 最多只能活 6 小时，
   "等"顶多 5 小时半 —— **L 超过 ~5.5 小时就必须拆成两个 job 接力等**
   （run 的总时长不受限制，只有单个 job 受限）。
   实测参考：凌晨那时段晚 2.8~5.0 小时，下午/晚间起的 cron 晚 5.2~7.6 小时。
4. **cron = T − L**（换算成 UTC）。
5. **每一棒的 `MAX_WAIT` 卡在中间**：要大于那一棒要等的时间，又要明显小于 12 小时 ——
   它是防"排队跨过 UTC 零点"的保险（跨零点后 `date -u +%F` 翻到第二天，
   diff 会被算成 20 多小时，白等一整天）。
6. **随机抖动要算进等待预算里**，不能单独叠在睡眠之上 —— 否则
   `等待 + 随机 + 脚本` 会顶爆 `timeout-minutes`。
   （这个坑踩过：随机曾是独立一步、叠在 5.5 小时睡眠之上，最坏 5h50m + 脚本，直接顶爆。）

> **别用整点（:00）**。GitHub 的定时器在整点附近统一派活，整点最挤，
> 会推迟几分钟到一两个小时，严重时整次漏跑 —— 实测整点的 cron 迟到过 1 小时 32 分。
> 分针随便挪，别落在 0 就行。

> 想改成别的时间，要**同步改两处**（只改一处会跑偏）：
> ① `schedule:` 那行 cron（写 UTC，北京减 8 小时）；
> ② `NEWS_DAY` 那行 —— 它决定这次看"昨天"还是"今天"的要闻。现在固定看**前一天**，
>    且**别改成靠"现在几点"去猜**：排队晚点可能跨过中午 12 点，靠猜会把内容切错。
>
> 完整方法论 + 覆盖范围仿真脚本见技能 `gh-actions-schedule-diagnosis`。

## 几个设计细节（为什么会这样）

**1. 按源轮转挑选，不是从头顺着拿。**
如果某个源一天条目特别多，顺着拿会把别的源全挤掉。所以是「每个源先各拿 1 条，再各拿第 2 条」这样分配。

**2. 去重靠索引文件，不是靠时间。**
推送过的链接存进 `state/seen.json` 并提交回仓库，下次只推没见过的。所以同一篇旧文章最多烦你一次。

**3. 只在内容真的变了时才提交；保活交给一个低频 workflow。**
`state.py` 写盘前会先比一次指纹：只有时间戳变了、内容没变就跳过写盘，所以没有新内容的日子**不会**产生提交（安静下来就不会有一堆没意义的提交）。
但仓库 **60 天无提交**会被 GitHub 禁用定时任务（这是它唯一的机制，静默生效、被禁后没法自救），所以另有一个 `keepalive.yml`：**每月 1 号**看一眼，距上次提交超过 20 天才补一个提交——一个月最多一次，平时它什么都不做。

**4. 消息长度双保险。**
企业微信 markdown 上限 4096 字节，组装时按字节数边加边算，超了就拆条；实在拆不动的单条由 `push._truncate` 按行兜底。

**5. 首次运行记的是"全部候选"，不是要推的那几条。**
如果只把准备推的 24 条记进索引，剩下的会在之后十来天里被当成"新内容"陆续推出来，等于给你补一星期旧闻。所以 `main.py` 里首次运行走的是 `eligible_by_source()`，把候选池整个记进索引。

**6. 干跑（`dry_run`）什么都不写盘。**
预览时不推送、也**不把内容标记成已推送**，否则"看一下效果"就会悄悄把当天的新内容吃掉，下次真跑反而什么都没了。想在本地看完整效果用 `simulate.py`（它用临时目录里的副本，仓库绝对干净）。

## 出问题了怎么查

**Actions 里没有 `gk-daily-push`** → `daily.yml` 位置错了。

**收到「运行失败」推送** → 消息里带了错误类型、信息和日志尾部。
最常见的两种：`没配 WEWORK_WEBHOOK`（Secrets 没配或名字打错）、`所有源都没抓到内容`（网络或站点改版）。

**某个源条数总是 0** → 去 Actions 日志看「源【XX】没解析出条目」，说明站点改版了，需要更新它的 `pattern`。
单源挂掉不影响其他源，也不会让任务失败。

**企业微信收不到** → 手动 Run workflow 测一次；还不行就检查 Webhook 是否复制完整（末尾 `key=xxx` 不能少）。

**好几天没收到推送，Actions 里连新运行都没有** → 先看定时任务是不是被 GitHub 禁用了（仓库 60 天没提交就会这样）：Actions 左侧点 `gk-daily-push`，顶部有黄色提示就是它，点 **Enable workflow** 即可。也可以手动 Run 一次 `keepalive`。
